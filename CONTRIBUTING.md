# Contributing

Two kinds of contribution matter here, and they have different bars.

## 1. Correcting rule data — always welcome, low ceremony

This is the most valuable thing you can do. Every rule in `data/` carries a `source` URL and a
`verifiedAt` date; if one is wrong, out of date, or missing, that is a bug of the most expensive kind.

1. Change the JSON in `data/`, not the code.
2. Point `source` at an **official portal or operator page** — not a blog, not a comparison site, not a
   reseller. If the only source you can find is unofficial, open an issue instead; a documented gap is
   better than a sourced-to-nowhere rule.
3. Set `verifiedAt` to the day you personally looked.
4. Add a test in `test/resolve.test.ts` that fails without your change.
5. `npm test` — the suite also enforces unique product ids, valid class references, no URL outside the
   official allowlist, and no verification date in the future.

Prices in this region change every January and February. A PR in February that re-verifies all six
country files with new dates is a great PR.

## 2. Adapters — welcome, with proof of a real run

The maintainer drives CZ, AT, SI, SK and HU. Adapters for other countries are welcome, but untested
browser automation in someone else's repository is a liability, and here the liability is somebody's
fine.

**A PR that adds or changes an adapter must include a record of a real run.** Concretely:

- Which portal, which product, which date you ran it.
- The `check` output before and after (redact the plate to a shape, e.g. `1AB••••`).
- Where the run stopped: for `purchase`, a screenshot or transcript showing it stopped **at** the
  payment gateway.
- What happened when you broke it on purpose — the manual handoff it fell back to.

We are not asking for a receipt. We are asking for evidence that the code has met the real portal.

### An adapter must

- return a `ManualHandoff` on any portal-shaped failure, never `throw`;
- return `{ outcome: 'ok' }` from `check` **only** when the portal actually said so;
- stop at the payment gateway in `purchase`, always;
- call `journal.canProceed()` before, and `journal.record()` before, every step that costs money.

See [docs/adapters.md](docs/adapters.md) and [docs/safety.md](docs/safety.md).

## What will be declined

- Anything that links a reseller, an affiliate, or a "comparison" site. There is a test for this and it
  is not negotiable.
- Anything that stores card details, submits a payment, or works around SCA.
- Anything that hosts: a backend, a database, a shared cache of plates.
- Rules generated by asking a model. If it does not have an official source and a date, it is not data.

## Development

```bash
npm install
npm test          # vitest
npm run typecheck
npm run cli -- plan --route CZ,AT --from 2026-07-15 --to 2026-07-20
npm run mcp       # stdio MCP server
```

Node ≥ 20.10. No Python anywhere in this project.

## Language

Code, comments, tests, commits and docs in English. `README.cs.md` and `docs/kickoff.cs.md` are kept in
Czech because that is the audience; rule text in the data files carries both `en` and `cs`.
